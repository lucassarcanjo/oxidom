# API surface census: jsdom vs happy-dom vs oxidom

> Committed here: the summaries (re-run on 2026-10-19 in this repository; identical numbers to the lab baseline of 2026-10-17). The large outputs (`results/idl.json`, `results/runtime-*.json` and `results/surface.json`) are gitignored and
> regenerated by a run; the baseline copies stayed in oxidom-lab.

This directory measures how much of jsdom's API surface happy-dom and oxidom expose. Everything is computed by scripts and can be re-run. It answers two questions. How far is oxidom from "everything jsdom has"? Where do happy-dom and jsdom differ? It measures **presence only**: a member that exists may still be a stub or behave differently. Behaviour is out of scope here.

## Re-run

```sh
./run.sh            # about 10 s; needs e2e/react-app/node_modules and packages/oxidom/native/*.node
```

`run.sh` runs these steps:

1. `node parse-idl.mjs` parses all 227 `refs/jsdom/lib/jsdom/living/**/*.webidl` files with `webidl2` 24.5.0 and writes `results/idl.json`.
2. `node probe.mjs jsdom|happy-dom|oxidom` runs once per DOM, each in its own process, and writes `results/runtime-<dom>.json`. A probe:
   - captures plain Node's `globalThis` descriptors first;
   - installs the DOM on `globalThis` the same way Vitest 5 does. jsdom and happy-dom use `builtinEnvironments[...]` from `e2e/react-app/node_modules/vitest/dist/runtime.js` (vitest 5.0.5, jsdom 30.1.3, happy-dom 21.0.3). oxidom uses `packages/oxidom/lib/vitest-environment.mjs` `setup(globalThis)`;
   - dumps raw facts: each global's type, whether it is still Node's own value, the prototype chain and constructor chain of every interface (own keys per level), own keys of one representative instance per interface, and the names reachable on the window.
3. `node analyze.mjs` compares the dumps with the IDL. It writes `results/surface.json` (the full per-member matrix), `results/summary.md` (per-area tables and ranked gaps) and `results/missing-members.md`.

Every step is deterministic, and repeated runs give identical counts.

## What is counted

**Interfaces.** The census covers every `interface` and `namespace` in jsdom's IDL that is exposed on Window: 209 in total. Partial interfaces are merged, and `includes` mixins are copied into each interface that includes them. Callback interfaces are left out unless they are exposed. `NodeFilter` is the only exposed one, and only its constants count. `[NamedConstructor]` (legacy factory functions `Image`, `Audio`, `Option`) are recorded with each interface.

**Members.** A member is an attribute, operation, constant, static attribute or static operation, a stringifier (counted as `toString`), or an iterator method. `iterable<>` yields `entries`, `forEach`, `keys`, `values` and `@@iterator`; maplike and setlike yield their methods. Overloads are deduplicated, which leaves 1877 members. Indexed and named getters, setters and deleters are not prototype properties. They are listed per interface in `surface.json` under `specials` and are not probed or counted.

**Denominator.** The denominator is what jsdom actually exposes on its Vitest global. That turned out to be all 209 interfaces and 1877 members (`jsdomIdlGaps` is empty), which validates the method.

**Interface presence.** An interface is present when `typeof globalThis[Name]` is `'function'`, or `'object'` for the `CSS` namespace and for callback interfaces. If an interface is missing, all of its members count as missing, as the task requires. This holds even when instances exist. For example, happy-dom's `classList` is a DOMTokenList but `globalThis.DOMTokenList` is undefined. `summary.md` lists these cases separately as information only.

### Member status per DOM

| code | meaning | counted as present |
|---|---|---|
| R | Own property of the right object. That is the interface prototype for regular members, the constructor for statics and constants, the namespace object, or the instance for `[LegacyUnforgeable]` (`Location.*`, `Document.location`, `Event.isTrusted`) | yes |
| C | Reachable through the interface's prototype chain but defined on another object. Example: happy-dom's global `Document` is a per-window subclass, so its members sit one level up | yes |
| O | Own property of a real instance only, i.e. a class field. Example: happy-dom `MouseEvent.clientX`. It is usable in tests, but prototype-descriptor tricks cannot see it. React's value tracker and user-event's interceptors read `Object.getOwnPropertyDescriptor(proto, ...)` | yes |
| S | Not on the interface or its ancestors, only on a subclass prototype. Example: happy-dom has `clientWidth` on HTMLElement instead of Element, so SVG elements lack it | **no** |
| M | Missing (the interface is present) | no |
| I | The interface is missing from the global | no |

"Present anywhere in chain" corresponds to R+C+O, and "on the right interface" corresponds to R. Representative instances come from `createElement` for about 120 tags, `createElementNS` for SVG, factory calls such as `createRange`, `classList`, `style.sheet.cssRules[0]` and `MutationRecord`, and generic `new C('x')` / `new C()` / `new C('x', {})`. An instance is credited to interface I only when `Object.getPrototypeOf(instance) === I.prototype`. If no exact instance exists, a fallback credits instances of a subclass, except for EventTarget, Node, Element and HTMLElement.

**Constructibility.** Each interface's `construct` field records the result of `new C()` with no arguments: `ok`, `needs-args`, `illegal` or `error`, plus the message. It is informational and never counted.

## Supplements (jsdom surface outside `living/*.webidl`)

- **Window.** jsdom has no `Window.webidl`; `browser/Window.js` writes the members by hand. The census derives the Window member list from jsdom's real window object (`globalThis.jsdom.window`). It removes JS-language builtins, which are taken from a fresh `vm` context, along with interface objects, `_internal` names and the EventTarget level. That leaves 180 members, 10 of which plain Node also has. A name counts as present in a DOM when it is reachable on `globalThis` and its value is not `undefined`, or when the DOM's real window has the key. This rule exists because Vitest's `populateGlobal` defines a getter for every name in its KEYS list even when the DOM lacks it. Under jsdom, for example, `matchMedia` is in KEYS but evaluates to `undefined`.
- **Other runtime interfaces.** jsdom also installs URL, URLSearchParams (from whatwg-url), CSSStyleProperties (generated from the CSS property list), XPath* and the HTMLDocument alias. Their members come from jsdom's runtime prototypes. CSSStyleProperties is reported separately because it has 1640 accessors (753 of them camelCase and unprefixed). Those are checked on each DOM's `document.body.style` instance chain.

## Area rules (`classify()` in parse-idl.mjs; the first match wins)

1. These names are always **Forms & constraint validation**: HTMLFormElement, HTMLInputElement, HTMLSelectElement, HTMLTextAreaElement, HTMLButtonElement, HTMLFieldSetElement, HTMLOutputElement, HTMLOptionElement, HTMLOptGroupElement, HTMLLabelElement, HTMLLegendElement, HTMLDataListElement, HTMLMeterElement, HTMLProgressElement, HTMLFormControlsCollection, HTMLOptionsCollection, RadioNodeList, ValidityState, FormData, SubmitEvent, ElementInternals.
2. ShadowRoot, HTMLSlotElement, HTMLTemplateElement and CustomElementRegistry are **Custom elements & Shadow DOM**.
3. Node, Element, Document, XMLDocument, DocumentFragment, DocumentType, CharacterData, Text, CDATASection, Comment, ProcessingInstruction, Attr, NamedNodeMap, NodeList, HTMLCollection, DOMTokenList, DOMStringMap, DOMImplementation, EventTarget, DOMException, QuotaExceededError, AbortController and AbortSignal are **DOM core**.
4. Names matching `SVG*` are **SVG**. Names matching `CSS*`, `*StyleSheet*` or `MediaList` are **CSSOM**. Names matching `*Event`, other than `Event` itself, are **Events**. Names matching `HTML*Element` are **HTML elements**.
5. Otherwise the directory under `living/` decides: events and deviceorientation go to Events; css to CSSOM; svg to SVG; range, traversal and selection to Traversal, Range & Selection; domparsing to Parsing & serialization; window and navigator to Window, navigation & history; xhr, fetch and websockets to Networking; file-api to File API; webstorage to Storage; encoding to Encoding; custom-elements to Custom elements & Shadow DOM; mutation-observer to Mutation observers; geometry to Geometry; constraint-validation to Forms; aborting, webidl and attributes to DOM core; hr-time and crypto to Misc.
6. Plugin, PluginArray, MimeType and MimeTypeArray go to Window, navigation & history. Anything else falls into Misc.

## Obsolete features

Members that jsdom declares in `partial interface HTML*Element` blocks are tagged `obsolete`. These include `align`, `bgColor` and `compact`. All of these partials are the HTML spec's obsolete-features section, except HTMLElement's partial, which is CSSOM View. Six whole interfaces are tagged as well: HTMLMarqueeElement, HTMLFrameSetElement, HTMLFrameElement, HTMLDirectoryElement, HTMLFontElement and HTMLParamElement. `summary.md` gives totals both with and without these, and also without `on*` event-handler attributes. Those handlers make up 339 of the 1877 members, because mixins such as GlobalEventHandlers are counted on every interface that includes them. The test is `/^on[a-z]/`, so `navigator.onLine` is not counted as a handler.

## Reverse census

The reverse census lists what happy-dom and oxidom have that jsdom lacks:

- globals that are not in plain Node's `globalThis`, not JS builtins, and not on jsdom's window or global;
- prototype and static members of interfaces that both DOMs expose but that appear nowhere in jsdom's chain.

jsdom's instance-own unforgeable members and its CSSStyleProperties accessors are taken into account. Numeric index accessors that oxidom defines on prototypes (`0..N`) are reported as a count, not as API names. `Object.prototype` names such as `toString` are filtered out.

## Importance ranking

`importance.mjs` is a hand-curated list of about 380 keys in tiers P0, P1 and P2. The tiers are a judgement, not a measurement. They are based on docs/lab/research/testing-library.md §7 and §12, react-dom.md §11 and §12, app-notes.md, and common library usage (msw/axios use XHR, upload tests use File/FileReader, routers use history/location, web components use customElements). `summary.md` lists the missing keys per DOM. It also has a separate table of curated keys that jsdom itself lacks, such as `innerText`, `scrollIntoView`, `matchMedia` and the dialog methods, so that they are not counted against anyone.

## Caveats

- Presence does not mean behaviour. oxidom's layout getters return zeros, for example, and so do jsdom's and happy-dom's.
- The probe reads the global the way Vitest builds it, and Vitest changes things:
  - Node globals that are not in Vitest's KEYS list stay Node's. Under jsdom that applies to AbortController, AbortSignal, Headers, TextEncoder and TextDecoder.
  - KEYS names a DOM lacks become getters that return `undefined`. Under happy-dom this hides Node's own `Crypto` and `Performance` classes.
  - `surface.json` records `fromNode` for each interface.
- In happy-dom the global constructors for Document and others are per-window subclasses, and many members are class fields. That explains its low "right interface" share (50%) compared with its "present" share (72%).
- Instance-own checks (status O) only work where the probe could build an instance: 158 of 209 interfaces in happy-dom.
- Indexed and named property access (`list[0]`, `form.elements.name`) is not probed.
- happy-dom ships many interfaces jsdom lacks (about 150, mostly SVG and media). They are not part of the denominator; see the reverse census.
