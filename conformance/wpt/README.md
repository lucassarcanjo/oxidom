# conformance/wpt — WPT behavioural conformance in Vitest global-install mode

> Committed here: the summaries of the 2026-10-17 baseline. The large outputs (`results/raw/`, `results/wpt.json` and `results/selection.json`) are gitignored and
> regenerated by a run; the baseline copies stayed in rsdom-lab.

Runs the web-platform-tests that jsdom itself runs (the DOM-environment-relevant subset of
`refs/jsdom/test/web-platform-tests/to-run.yaml`) against **jsdom 30.1.3, happy-dom 21.0.3 and rsdom**, each
installed on `globalThis` by its Vitest environment, and counts per-subtest PASS/FAIL. The numbers answer
"how much of the behaviour jsdom implements (and tests) do happy-dom and rsdom implement?"

Outputs (in `results/`):

| file | contents |
| --- | --- |
| `selection.json` | the exact test list (2389 files) with each file's scripts and jsdom's expectation, plus every excluded test grouped by reason, DIRs run / not run |
| `raw/<dom>.jsonl.gz` | one line per test file per DOM: harness status, every subtest's status + message (≤400 chars), script errors, timing |
| `wpt.json` | per file: harness status per DOM, and `subtests[name]` = 3-letter status string (jsdom, happy-dom, rsdom; P/F/T/N/X/M/C, legend inside) |
| `globals.json` | per DOM environment: whether each relevant global is the DOM's, Node's own, or absent (`probe-globals.mjs`) |
| `summary.json` | totals, per-area numbers, top failure causes per DOM, the jsdom fidelity check, files/areas where happy-dom or rsdom beat jsdom |
| `summary.md` | the same as a readable report |

Needs `e2e/react-app/node_modules` (jsdom, happy-dom, vitest, parse5), `rsdom/node_modules/js-yaml` and the release addon

## Method

**Test universe.** jsdom's own `wpt-manifest.json` (generated at WPT commit
`2971340498805350babb6c167e0df98eaa380f98`) lists every testharness URL; `to-run.yaml` lists the 127 DIRs jsdom
runs. We keep the 67 DIRs that exercise a DOM test environment (dom/*, domparsing, domxpath, encoding API,
FileAPI, css/cssom, css/selectors, custom-elements, shadow-dom, uievents, selection, webstorage, xhr, html/dom,
html/semantics/* except canvas, html/syntax, html focus/activation, html/webappapis event handlers/timers/atob/
microtasks). The 60 DIRs not run (crypto, cookies, fetch, url, websockets, navigation/history, CSS layout
modules, SVG, canvas, device APIs) are listed with a reason in `selection.json` → `dirsNotRun`.

**Exclusions** (first matching rule wins; counts in `selection.json` → `exclusionCounts`): jsdom's own global
filters (worker variants, testdriver, shadowrealm, tentative), then everything needing wptserve or a real
browser: `.sub.`, `.https.`/`.h2.`, server-side handlers (`.py`, `?pipe=`), cross-origin helpers, idlharness
(fetches `.idl` files), network fetch/XHR send, iframes / second documents / `window.open`, workers, module
scripts, navigation/history, `document.write` (parser-interleaved), media resources, legacy-encoding pages,
charset sniffing, the html5lib driver (fetches `.dat` files and parses in iframes). Content rules scan the
test file and its test-specific helper scripts (the iframe rule skips four multi-purpose helper libraries
where only some functions open a second document — tests using those functions fail for all DOMs alike).

**Harness (global-install mode, identical for the three DOMs).** `worker.mjs`, in a fresh process per
(test file, DOM):

1. installs the DOM on `globalThis` with its Vitest environment object — `builtinEnvironments.jsdom` /
   `builtinEnvironments['happy-dom']` from `e2e/react-app/node_modules/vitest/dist/runtime.js`, and
   `packages/rsdom/lib/vitest-environment.mjs` — with environment url `http://web-platform.test:8000/<test path>`;
2. loads the markup: parse5 parses the page (or the wptserve wrapper page generated for `.any.js` /
   `.window.js`), then `document.documentElement.innerHTML = <serialized children of <html>>` plus the
   `<html>` attributes (scripts inserted this way never execute in any of the three DOMs);
3. runs `resources/testharness.js` and every classic `<script>` (inline, or same-origin file from the WPT
   checkout) **in document order** with `vm.runInThisContext`; `testharnessreport.js` is replaced by a hook
   that calls `setup({output:false, explicit_timeout:true})` and collects `add_result_callback` /
   `add_completion_callback`. It installs the same cross-realm `assert_throws_js` / `promise_rejects_js`
   shim as jsdom's own WPT runner (error `.name` instead of `instanceof`);
4. an exception thrown by a script, or an uncaught exception / unhandled rejection in the process, is
   reported to testharness as an `error` / `unhandledrejection` event dispatched on `window`;
5. dispatches `DOMContentLoaded` on `document` and `load` on `window`, then waits for completion; after
   10 s it calls testharness `timeout()` (TIMEOUT); the parent kills a process that has not answered after
   40 s (KILLED). A process that dies or a failed environment setup counts as CRASH/SETUP_ERROR.

One process per test file because top-level `let`/`const`/`class` of a page live forever in the global
lexical scope under `vm.runInThisContext` (a second page in the same process would fail with "already
declared"); Vitest with `isolate: true` also gives every test file a fresh worker. At most 2 processes run at
a time.

**Named access.** Browsers expose `<div id=foo>` as `window.foo`, and many WPT pages use such ids as bare
identifiers. Vitest's global install does not mirror named properties onto `globalThis` for any of the three
DOMs, so before the scripts run the harness defines a getter per id found in the markup, resolved through the
DOM's own `document.getElementById` (identical for all three; assigning or declaring the name replaces it).

**Counting.** A file's subtests are the union of subtest names the three DOMs reported; a subtest a DOM did
not report (harness error before it was defined, crash) fails for that DOM. A file where no DOM defined any
subtest counts as one pseudo-subtest that passes iff the harness status is OK.

## Fidelity limits (why jsdom scores lower here than in its own runner)

This is the environment Vitest users actually get, not a browser page load, so some WPT assumptions break —
for every DOM, but they show most clearly against jsdom's expectations (see the fidelity section of
`summary.md`):

- `window === globalThis` (Vitest's `populateGlobal`), but event paths, `defaultView`, `currentTarget` etc.
  hold the DOM's own window object; tests comparing them to `window` fail.
- Test code runs in the Node realm. jsdom's objects come from its own vm realm, so `x instanceof DOMException`,
  prototype identity, and `Object.getPrototypeOf(...) === Foo.prototype` checks can fail for jsdom;
  happy-dom's GlobalWindow and rsdom share the Node realm.
- jsdom compiles event-handler content attributes (`onclick="..."`) and dynamically inserted `<script>`s in
  its own realm, where the Node-realm testharness globals do not exist.
- Timers are Node's (Vitest does not install the DOM's timers), so `setTimeout("code")` throws.
- Scripts run after the whole markup is in the DOM, not interleaved with parsing; `document.currentScript` is
  null; `readyState` is already `complete`; the page's doctype / quirks mode is not reproduced (the
  environment's initial document is kept); external stylesheets and images are not loaded.
- 10 s per file regardless of `<meta name=timeout content=long>`.
- Some globals stay Node's own in a Vitest environment (`results/globals.json`): TextEncoder/TextDecoder in
  all three (so the `encoding` area measures Node and is excluded from the "excluding encoding" totals),
  AbortController/AbortSignal in jsdom and rsdom, Blob/File/URL/DOMException in rsdom.
- Dynamically named subtests (names built from DOM output) can differ between DOMs; the union then contains
  names a DOM never generated, which count as MISSING (failed) for it. Measured: 666 such subtests in 18 files
  whose harness was OK in all three DOMs (of 101,837 subtests in those files).

Fidelity check result (aggregate.mjs, `summary.md`): of the 2,123 selected files jsdom actually runs in its own
suite, jsdom-in-this-harness agrees with to-run.yaml on 1,954 files (92.0%) and on 109,238 of 110,077 compared
subtests (99.2%). The disagreements are classified in `summary.md`; the large groups are page-load semantics
(parser-interleaved scripts, doctype/quirks, charset, readyState), `window !== globalThis`, jsdom-realm code that
cannot see Node-realm test globals, Node's TextDecoder, and 19 files where jsdom now passes tests it expects to
fail.
